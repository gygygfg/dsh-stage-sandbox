### 3.3 **D2（refuted）删除"真实预存文件"后，白条没有参与枚举过滤**

`v4`：

```
STEP4_del=ok
STEP4_exists=False  STEP4_testpath=False  STEP4_read=THREW MethodInvocationException   ← open 面：确实没了
STEP4_gci=MX,OV,real.txt                 ← 枚举面：还在！
STEP4_netsfe=MX,OV,real.txt              ← .NET 面：还在！
STEP4_cmddir=[real.txt|MX|OV]            ← cmd 面：还在！
```

**真实磁盘真相**：`real.txt` 依然在盘上（8 B）——这是对的，白条语义就是"盘上留着、逻辑上删除"。
**白条标记也真的建了**：

```
<stage-root>\staged\wo\C\Users\…\verify\v4\ws\real.txt     （0 字节）
<stage-root>\staged\wo\C\Users\…\verify\v1\ws\r_only.txt    （0 字节）
```

于是形成**同一个产品的两个面互相矛盾**：`File.Exists=False` / 读取抛异常，但目录枚举照样把它列出来。
`v1` 同形（`G_del_r_only_ok exists_after=False` 之后 `G_ROOT_AFTER=.t,MIX,r_only.txt,seed.txt`，
`GSFE_root` / `GCI_root` 仍含 `r_only.txt`，`cmd dir` 也仍列出）。

**根因（读码，`shim/src/ws_dirfind.c`）**——白条过滤**只加在 staged 侧**（:495），真实侧没有：

```c
/* 真实层：逐个加入，无任何白条判据 —— :442–462 */
realRaw++;
if (wfd.cFileName[0] && wcscmp(wfd.cFileName, L".") && wcscmp(wfd.cFileName, L"..")) {
    WsFindEntry *p = ws_ent_grow(ents, count);
    …
    ws_ent_from_data(&ents[count], &wfd);
    count++;
}
…
/* staged 层：这一侧才问白条 —— :487–495 */
if (wfd.cFileName[0] && … && (pattern[0] == 0 || ws_match_w(pattern, wfd.cFileName))) {
    …
    if (ws_logical_present(logical)) { … }      /* ← 唯一一处白条判据 */
```

而 `ws_logical_present()`（:122）问的正是 `g_orig.GetFileAttributesW(logical)`，
**这个探针会正确报告白条**（盘上还有字节却返回 `INVALID_FILE_ATTRIBUTES`）。
但删除真实文件时，staged 侧**根本没有同名条目**（白条触发的前提是"staged 里有 copy"），
所以 :487 那轮循环连那个名字都看不到，唯一那处过滤自然不会执行。

⇒ 最小修法：在构建 `ents` 的**真实侧循环里**、`ws_ent_grow` 之前补一次
`if (!ws_logical_present(ws_join(path, wfd.cFileName))) continue;`（与 staged 侧同源判据）。

**为什么尝试 2 的 8/8 全绿没抓到**：它的 D 段是**先写 overlay 再删**（`[IO.File]::WriteAllText` 建 `gone.txt` 再删），
走的是"staged 里先有条目、再打白条"这条**有过滤**的路径；`Lead` 的验收件同样只测了这条路径。
**"真实预存文件被删除"（R11 原始症状的那一类）没有一条验收覆盖到。**

| 异步 `spawn` + pipe | **整进程崩溃**（`read ENOTCONN`），无 `close`/`REACHED-END` |
| `spawnSync` 默认 pipe | `status=null out=undefined err=ENOENT`，脚本继续（不崩） |
| `spawnSync` 文件重定向 | `E3 status=0`（正常） |
| `Process.StartInfo.RedirectStandardOutput` | `E4 status=0 out=PIPED`（正常） |

**更关键：新增的 `spawnCaptured()` 在该环境里**根本不会**触发降级**（`.t/r12/verify/v6/extract/…`）：

```
EXPORTS=PIPE_REFUSAL_CODES,__setPipeRunnerForTest,installChildProcessPipeGuard,isPipeRefusal,pipeRefusalState,spawnCaptured
isPipeRefusal_ENOENT=false          ← ★ 本环境的管道拒绝码是 ENOENT，而 ENOENT 不在拒绝族里
isPipeRefusal_ENOTCONN=true

CMDCAP via=pipe status=null out="" pipeError=undefined              ← 连 cmd.exe 也拿不到输出
FILEMODE via=file status=0 out="42\n"                               ← 显式 mode:'file' 是好的
```

对照 `src/child-capture.mjs:45`：

```js
export const PIPE_REFUSAL_CODES = Object.freeze(['EPERM','ENOTCONN','EACCES','EPIPE','EINVAL','UNKNOWN','ERR_CHILD_PROCESS_STDIO_MAXBUFFER'])
```

**没有 `ENOENT`**；而 `spawnCaptured` 的判据是 `!isPipeRefusal(piped.errorObject) ⇒ return piped`（:97），
于是 `ENOENT` 直接被当成"普通失败"原样返回，**既不重试文件重定向，也不附 `pipeError`/`note`**，
结果是"**静默的空输出**"——比崩溃更隐蔽（审计面看到的是 `status=null`，看不出是管道受限）。

⇒ 判定：**"崩溃已修"不成立（原崩可复现）；"降级机制已就位"也不成立（该环境不可达）**。
修法很小：把 `ENOENT` 收进拒绝族（或把判据改成"`status===null && (errorObject||stdout==='')` 时试一次文件重定向"），
并在 CI 里加一条"异步 spawn + pipe 不得整进程死亡"的用例——这条现在是**裸的**。

**第三次复现（排除 shell 引号假象）**：为防"v5 的崩溃是 `-e` 被 shell 搞坏导致的假阳性"，
