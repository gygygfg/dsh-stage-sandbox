## 1. 逐条修复

### U16-5（P2）CLI `--help` 退出码 2；子命令 help 不覆盖真实参数

- **根因**：`src/cli.ts` 把 `--help` 和无参当成同一件事（`if (!command || flags.help) { … exit(command ? 0 : 2) }`
  ⇒ 无 command 时恒 exit 2）；`USAGE` 只列 `--workspace/--json/--session`，而代码实际支持
  `--candidate/--paths/--force/--max-lines/--timeout/--tier/--read-only/--no-cache/--use-cache/--reason/--apply`。
- **改法**：`--help`/`help [命令]` 一律 **exit 0**；新增 `COMMAND_USAGE`（逐子命令的真实参数），
  `usageFor()` 作为帮助文本的单一来源；无参仍是用法错误（exit 2）并给命令表。
- **证据**：`tests/cli-contract.ts` §1（9 项）；`.t/r18-thread2.ndjson` 的新 DSH 线程读数。

### U16-6（P2）候选不存在时抛未捕获堆栈

- **根因**：`diff/apply --candidate <不存在>` 直接把 `SandboxError` 冒到顶层 `catch`，输出
  `未捕获错误: SandboxError: … + 栈帧`，与同仓 `USAGE: …` / `CODE: message` 风格不一致。
- **改法**：`resolveCandidateOrFail()` 把 `CANDIDATE_NOT_FOUND` 转成结构化错误（`CANDIDATE_NOT_FOUND: …` +
  下一步提示"先跑 review"）；顶层 `catch` 对 `SandboxError` 输出 `CODE: message`（不再打栈），
  未知异常才保留堆栈。
- **证据**：`tests/cli-contract.ts` §2（10 项，含"无栈帧"负断言）。

### U16-7（P2）`status` 回显入参 + exit 0 + 静默读别的 store

- **根因**：`--workspace` 不校验存在性；`Store.manifest()` 只"有就返回"，不校验
  `manifest.workspaceRoot` 与当前工作区一致 ⇒ 环境变量/会话键不同时会给出**另一个 store** 的读数；
  `status` 也从不打印解析后的 store 根。
- **改法**：① `--workspace` 不存在 ⇒ `WORKSPACE_NOT_FOUND`（非 0 退出；`probe` 保持宽容）；
  ② `manifest.workspaceRoot` 与当前工作区不一致 ⇒ `WORKSPACE_STORE_MISMATCH`（fail-fast，点名两个根）；
  ③ `status` 文本打印 `存储根 : …`，`--json` 增加 `storeDir`。
- **证据**：`tests/cli-contract.ts` §3（7 项）。

### U16-8（P2）`exec` 文本模式不显示档位

- **根因**：`tier/tierEffective/launchMode` 只在 `--json` 的 `sandboxInit` 里，文本模式只打印
  `退出码/分类/用时`。
- **改法**：新增 `formatExecTierLine(sandboxInit)`（`tierEffective ?? tier` + `launchMode`），
  `exec` 文本输出补一行 `档位=<tierEffective>(<launchMode>)`，与 `sandbox-lane.json` 同源字段。
- **证据**：`tests/cli-contract.ts` §4（3 项）；纯函数可从模块直接 import（见下条）。

### U16-9（P2）描述字段的 markdown `**` 原样显示（R11 D7-e 复现）

- **根因**：`dsh-plugin/client.ts` 中/英文字典串里混入 markdown 强调标记，面板按纯文本渲染 ⇒ 星号原样显示。
- **改法**：去掉 4 组中英文用户可见字典串里的 `**`（设置项说明、设置失败说明、可信性降档、档位信息不完整）。
- **证据**：`tests/cli-contract.ts` §4 的字典扫描（0 处）；改后 `dist/client.js` 已重建。

### 顺带的可测性改造

`src/cli.ts` 的顶层 `main()` 改为**仅在直接执行时**运行（`pathToFileURL(process.argv[1]) === import.meta.url`），
这样套件可以 `import` 纯渲染函数（`usageFor` / `formatExecTierLine`）而不会被 CLI 副作用带跑。

## 4. 验证方式（"新 DSH 线程"而不是本线程自证）

本线程按任务纪律**不加载沙箱**。验证用两路互相独立的读数：

1. **干净进程关口**（`packages/win/.t/r18-seal-verify.cmd`）：重建 `dist` → 重封基线 → `verify.cmd`
   ⇒ `ALL PASS`。之所以从"干净进程"起，是因为被暂存的 shell 里 `stage-guard` 的 `Add-Type`
   临时文件会被暂存层拦住（这是会话形态限制，不是产品失败）。
2. **新 DSH harness 线程**：用 headless profile 模板新建 `profile=sbxr18`（bundles：
   `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-headless` + `dsh-winstage-sandbox`），
   由**未受限的 WMI 进程**启动（`WINSTAGE_SHELL=1`、独立 `WINSTAGE_STAGE_ROOT`、清空 `DSH_SESSION_ID`），
   让它在自己线程里跑三条命令并回报。原始事件：`packages/win/.t/r18-thread2.ndjson`
   （该线程的 shell cwd 被重定向到 `<stage>/staged`，证明沙箱在本线程之外**真实装配**）。

## 5. 仍未修 / 本轮明确不声称的（诚实清单）

按 round16 汇总 §6 的排序，以下**仍然未修**（都需要重建 C shim 或属产品决策，不在本轮范围）：

- **P0 shim 覆盖面**：显式 32 位视图注册表键创建/删除仍 `UNSTAGED` 透传真 hive（`ws_reg.c`）；
  `NtCreateFile` 未挂钩 ⇒ COM/`WScript.Shell.CreateShortcut().Save()` 等仍可直写真实盘。
  R15 记录的重建件把 lane 打到 T1 的根因未定 ⇒ 本轮**不重建 shim**（重建即不可验证）。
- **P0 注册表候选**：`shell-executor → registry-capture` 已接线，但"真机写注册表一定产生候选"仍待
  新的真机 run 复验（本轮无真机注册表 E2E）。
- **P1/P2 目录与文件语义**（`fs.existsSync` 假阴、`rmSync(recursive,force)` 静默不删、`mkdirSync` ENOENT、
  ADS 改写、长路径阈值）—— 同源于 golden shim 不含目录枚举修复。
- **P1** D2-R16-1（pip 全局镜像配置 WinError 5）、D6-1（写意图 open 的明文 copy-up）、
  D6-3（工作区种子脚本不可执行）、D6-4（~30 次操作后全线失败）、U16-1（混合态可见性，产品决策）。
- **P2** 网络审计面不记录逐条 op / `audit.jsonl` 非标准 JSONL（写入端在 shim）；
  `status/review/diff` 之外的 store 根打印、`/health` 等 web 宿主能力（平台侧）。

本文件**不**声称"沙箱隔离成立"或"上述残余已消除"；它只覆盖 §1 列出的 6 条 CLI/易用性缺陷。
